## 为什么交付目录大

以下是完整重建后的工作树，而不是 Git 仓库下载量、邮件压缩包或游戏安装包。测量绑定到技术候选提交 `3c368437dd9df0f7a4589ce3e8f452bf7de1e164`，未修改任何模型。

完整树8038文件（8032资产+6辅助），3,509,029,574字节；其中PNG约2.448 GB、Blend约666 MB、FBX约355 MB。仅名为 previews 的文件夹内PNG就1.064 GB。源树保留图册素材、重复外置纹理、独立版本和组合场景，因此不能按其大小估算游戏资源。

全文件SHA-256去重测得额外同内容副本约1.076 GB。textures/ProjectFiles路径中PNG共1.209 GB，重复额外副本约1.044 GB。这里只是可研究的存储机会，没有删除或重定位文件。

实际只读打开101个Blend后，1473个嵌入PNG引用载荷共480,505,406字节，仅326种独立内容，共162,560,592字节；全部均能在外置PNG找到完全相同字节。分辨率引用数：4096²×188、2048²×613、1024²×283、512²×389。它们包含跨版本与组合场景重复，不等于1473种游戏纹理或显存占用。

例如HarperCourtyardAssembly是组合源场景，143,044,779字节，87嵌入图像引用（58×4K+29×1K），载荷131,767,983字节，但仅22种不同图像、56,335,972字节。不能将这个源场景称为单栋建筑游戏文件。嵌入载荷可能受Blend压缩，不可把上述机会简单相加。

证据：[汇总](size-summary-20261118.json)、[逐源嵌入图片尺寸/字节/SHA](packed-image-inventory-20261118.json)。图片记录由Blender读取 packed_file.data、size，再计算SHA-256；文件统计遍历重建完整树并按字节SHA分组。

## 安全的后续优化顺序
1. 作者源包、预览文档、候选导入包分开交付；为每个建筑明确优先版本和依赖，避免把组合场景/历史版本一起装进游戏。
2. 在新工作副本中试做按内容哈希存储的共享外置纹理库，输出时再按官方命名恢复；保留完整清单和校验。不直接删除当前路径，避免破坏相对路径、离线打开或恢复链。
3. Blend内共享图像数据块只能在检查颜色空间、alpha模式及节点引用后试验。同字节不同语义不能盲目合并。
4. 4K降2K会减少75%像素，但会损失细节；先做近远景对照与实际Editor测试。不能为压缩包小而全局降面/降纹理。
5. 源文件共享不证明CS2运行时共享。实际编译包、GPU压缩格式/mipmap、显存、载入时间与批处理须在Editor/游戏测量，目前均未证实。

只添加此导航与体积证据、README入口，以及Python缓存/系统杂项和明确工作输出目录的ignore。没有删除模型/旧版本、移动已跟踪文件、改写历史、更改Release/标签/哈希链或修改许可证。没有为清理而减少候选模型内容。

重建与渲染输出应放仓库外。若必须放仓库内，使用 `.local-work/` 或 `.local-cache/`；不要把这些目录当永久成果。发布所需PNG/FBX/压缩包继续按已有白名单审核，不能忽略所有证据JSON或用全目录ignore掩盖待交付模型。
